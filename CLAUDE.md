# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev       # Vite dev server
npm run build     # tsc (type-check, no emit) then vite build → dist/
npm run preview   # preview production build
```

No test runner or linter is configured in this repo. `npm run build` is the only correctness gate (TypeScript `strict`, `noUnusedLocals`, `noUnusedParameters`).

Deploy is automatic: push to `main` triggers `.github/workflows/deploy.yml`, which builds with secrets (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `VITE_BACKEND_URL`, `VITE_GOST_URL`) and publishes `dist/` to GitHub Pages. Vite `base` is `/Ebu.Gubkin/` — routing uses `basename={import.meta.env.BASE_URL}` in `App.tsx`, so local dev and Pages deploy resolve routes differently; don't hardcode absolute paths.

## Architecture

This frontend is one of three services that share a single Supabase project (see project instructions for full DB schema): a Node/Express "Биржа" (marketplace) backend, a separate Python/FastAPI "ГОСТ" backend, and this React app. It talks to both backends over plain `fetch`, and to Supabase directly for auth, direct-table reads, and Realtime.

**Two independent API clients, two env vars:**
- `src/lib/api.ts` — `apiCall(method, path, body)` wraps `fetch` against `VITE_BACKEND_URL` (the Биржа backend). It pulls the Supabase session token via `supabase.auth.getSession()` and attaches `Authorization: Bearer <token>`, JSON-encodes non-`FormData` bodies, and throws an `Error` with `.data` set to the parsed error body on non-2xx. Almost all marketplace/forum/wallet/admin data flows through this one function — reuse it rather than calling `fetch` directly.
- `VITE_GOST_URL` (the ГОСТ backend) is read ad hoc per-page (`Gost.tsx`, `GostChat.tsx`, `Admin/GostTemplates.tsx`) with its own inline `fetch` calls — there is no shared client for it. Pages guard on `if (!GOST)` and show a "не настроен" message when the env var is missing.
- `src/lib/supabase.ts` exports a single `supabase` client used for auth (`AuthContext`), direct profile reads, Storage (avatars), and Realtime subscriptions (chat).

**Auth/profile state** lives in `AuthContext` (`src/contexts/AuthContext.tsx`), sourced from `supabase.auth` + a direct `profiles` table `select`, not from the backend API. It exposes `session`, `user`, `profile` (includes `is_admin`, `is_owner`, `is_owner_was`, `balance`, `token_balance`, referral fields), and `signUp`/`signIn`/`signOut`/`refreshProfile`/`toggleViewAsAdmin`. Profile rows are created server-side by a Postgres trigger (`handle_new_user`) reading `nickname`/`ref_code` out of `signUp` metadata — the frontend never inserts into `profiles` directly (RLS blocks it; see `docs/TODO_BACKEND.md` "lock_writes" note). `useAuth()` throws if called outside the provider.

**Two admin tiers: owner vs rank-and-file admin (since 2026-08-20).** `is_admin` still gates the whole `/admin/*` tree (unchanged); `is_owner` narrows it further, both in the UI and — the real boundary — on the reshbirga backend (`adminMiddleware.requireOwner`, see `reshbirga/CLAUDE.md`). `pages/Admin/index.tsx`'s `NAV_ITEMS` carries an `ownerOnly` flag per entry (Дашборд/Финансы/Пополнения/Выводы/ГОСТ-шаблоны/Прогрев расписания/Журнал/VIP are owner-only; Споры/Форум/Заказы/Чаты/Модерация/Поддержка/Пользователи/Настройки/Справка are open to any admin, though the last two self-restrict their own content for non-owners). `AdminRoute` additionally redirects a real non-owner admin to `/admin/disputes` if they hit an owner-only path by URL. `Users.tsx` shows an "ВЛАДЕЛЕЦ" badge and the owner-grant controls only to `profile.is_owner` — the backend already omits `is_owner` per-row from `GET /admin/users` for non-owner callers, so a rank-and-file admin can't infer it either way. The GOST calculator's unlock check in `components/Navbar.tsx` also switched from `is_admin` to `is_owner` — it's owner-only for now, not just admin-only (still in development, see `docs/schema.md`/root `CLAUDE.md`).

**"Смотреть как админ" is a real toggle, not a UI simulation.** The sidebar button in `pages/Admin/index.tsx` (`ViewAsAdminToggle`) calls `AuthContext.toggleViewAsAdmin()`, which hits reshbirga's `POST /profile/view-as-admin` and refreshes the profile — this genuinely flips `is_owner` server-side, so owner-only backend routes really 403 while toggled (a direct URL/API call behaves exactly like a real rank-and-file admin sees it). Visible whenever `profile.is_owner || profile.is_owner_was` — `is_owner_was` is a separate, permanent "was ever granted owner" marker (see reshbirga `CLAUDE.md`) that keeps the restore path available even if a toggle step fails midway. There is no client-side-only "view as" context left in this repo (an earlier `AdminViewContext` approach was replaced by this — don't reintroduce it, the real toggle is simpler and also the only way `Navbar.tsx` outside `/admin/*` can see the change).

**Routing** (`src/App.tsx`) is one flat `react-router-dom` v6 tree under a single `Layout`, with three route-guard/layout patterns:
- `ProtectedRoute` — redirects to `/` unless `useAuth().user` exists (after `loading` resolves).
- `AdminRoute` — same, but gates on `profile?.is_admin`, **and** on MFA: if the admin has a verified TOTP factor but the session is only `aal1`, it renders a code prompt instead of the children. This is the single client-side MFA gate for the whole admin tree — the reshbirga backend rejects every `/admin/*` call from an `aal1` session with `{ code: 'MFA_REQUIRED' }`, so waiting for that error per page would mean handling it in ~16 pages. Enrollment UI is `pages/Admin/TwoFactor.tsx` (Supabase's native `supabase.auth.mfa.*` — no custom secret storage, no QR library); the post-login step is in `pages/Login.tsx`. Both the login step and the admin gate also offer backup-code recovery via the shared `components/MfaRecovery.tsx` → `POST /mfa/recover`, which *removes* the factor (a backup code can't produce an `aal2` session) — after it succeeds, password-only access works and the admin re-enrolls. Also redirects a non-owner admin away from owner-only paths, see "Two admin tiers" above.
- Nested layouts `MarketLayout` and `GostLayout` wrap sub-trees (`market/*`, `gost/*`) for section-local chrome (e.g. sub-nav); admin sub-pages nest under `AdminLayout` (`pages/Admin/index.tsx`) similarly.

Each of the four product sections (Биржа/market, Форум/forum, ГОСТ/gost, Кошелёк/wallet) is a flat set of page components under `src/pages/`, not separate route modules — new pages get added directly into the `Routes` tree in `App.tsx`.

**Design**: `DESIGN.md` (repo root) is the North Star / authoritative source for design decisions and exceptions; `docs/DESIGN_SYSTEM.md` is the detailed token/component reference and must defer to `DESIGN.md` if they ever disagree. Actual theme: dark violet glassmorphism (`accent #7c3aed`, `canvas #1a1140`, Sora typeface), with `teal-legacy` (`#14a89a`) as a deliberate, tokenized second accent for the Биржа section (not a bug — see `DESIGN.md`'s North Star section before "fixing" any teal you find there). `src/components/glass/` (`GlassCard`, `Button`, `Chip`, `Avatar`, `Stars`) is a small implemented component kit derived from the `design_handoff_glassmorphism/` mockups at repo root — check which pages actually import from `glass/` before assuming it's used everywhere.

**The admin guide is generated, not hand-maintained.** `src/pages/Admin/adminGuideText.ts` (rendered by `pages/Admin/Help.tsx`) is produced from `reshbirga/ADMIN_GUIDE.md` by `npm run sync-guide` — edit the `.md` in the reshbirga repo and re-run, never the `.ts`. It's a copy because Vite can't import outside its root. The markdown renderer itself (headings h1–h3, tables, lists, bold, inline code) lives in `src/lib/markdown.tsx` (`renderMarkdown`), shared between `Help.tsx` and the legal pages below — if a guide edit needs anything beyond that subset, the renderer has to grow first, and the change benefits both consumers.

`Help.tsx` renders the **full, unmodified** `ADMIN_GUIDE_MD` for owners, but a trimmed version for rank-and-file admins via a `filterForAdminTier()` function **local to `Help.tsx` itself** — it drops owner-only `##`/`###` sections and a handful of owner-only paragraphs (the `ADMIN_TEXT_CUTS` array) by pattern-matching the generated text, all at render time. This is a second, independent place content gets removed for non-owners, separate from `sync-guide`'s generation step — **never "fix" a rank-and-file-admin content problem by editing `ADMIN_GUIDE.md`**, that changes what owners see too; add/adjust a cut in `filterForAdminTier()` instead. `adminGuideText.ts` uses CRLF line endings, and the cut patterns match on `\n\n` — the filter normalizes to LF first (`filterForAdminTier`'s first line); a naive regex added later without going through that normalized string will silently no-op.

**Legal documents** (`src/legal/*.md` — `privacy.md`, `pdn-consent.md`, `terms.md`, `offer.md`, `market-rules.md`) render at top-level public routes `/privacy`, `/pdn-consent`, `/terms`, `/offer`, `/market-rules` via `pages/Legal.tsx` (imported as raw strings, `?raw`, and run through the same `renderMarkdown`). `Register.tsx` gates signup on two separate checkboxes — terms+offer, and PDN-consent+privacy — `disabled={loading || !acceptTerms || !acceptPdn}`; `Footer.tsx` links to all five. **Operator identity in `privacy.md`/`pdn-consent.md`/`terms.md`/`offer.md`** (the four that name an operator — `market-rules.md` doesn't) reads **"Администрация сайта «Ebu.Gubkin»"** with contact e-mail `ebugubkin@yandex.ru`, chosen deliberately over an ИП placeholder since the team isn't a registered sole proprietor/legal entity yet (as of 2026-08-25). If the team later registers a legal entity (ИП/ООО), replace this wording with real registration details (ФИО or company name, ИНН/ОГРНИП, correspondence address) in all four files before relying on these documents for anything requiring a registered counterparty (e.g. enforceable payment disputes).

**Reports export as .xlsx + a printed report document.** Three modules, no dependencies:
- `src/lib/reportData.ts` — `stampedName` (dated filename) and `fetchAllPages`, which every "export everything" path must use: PostgREST silently truncates at 1000 rows no matter what `limit` says, so a big `limit` quietly loses data.
- `src/lib/exportXlsx.ts` — hand-built `.xlsx` (store-only ZIP + inline-string sheet XML, ~140 lines). **Don't "simplify" this back to CSV**: in Excel the two CSV problems are mutually exclusive — the separator comes from the Windows regional list separator (so `;` collapses into one cell for some users), and the `sep=;` line that fixes it makes Excel ignore the UTF-8 BOM and mangle Cyrillic. xlsx has neither knob. Because the format is binary and hand-rolled, a mistake shows up as "Excel cannot open the file", which `tsc` cannot catch — run `npm run check-xlsx` (builds a file, re-parses the ZIP, verifies CRC32s, Cyrillic, emoji, numeric cells, column names past Z) after touching it.
- `src/lib/printReport.ts` — "PDF / печать" builds a standalone report document (header, filter parameters, full table, totals) in a hidden iframe and prints that, so output has no nav chrome and isn't limited to the visible page. The `@media print` block in `index.css` now only matters for ad-hoc printing of a live page. No jsPDF: Cyrillic there means embedding a TTF (~300KB–1.5MB base64) and hand-paginating — worth it only if a PDF must be produced with no human in the loop.

**DB write restrictions**: after migration `010_lock_writes.sql`, the frontend can only `UPDATE` safe columns on its own `profiles` row and `INSERT` into `messages`/`message_attachments` for itself — everything else (orders, transactions, disputes, wallet mutations) must go through the backend API (`apiCall`), never a direct Supabase mutation. Keep this in mind before adding a new Supabase `.insert()`/`.update()` call — check `docs/TODO_BACKEND.md` first.
